# Data files

Everything the model needs is under `data/`. All of it is declared game data or lists read from the running game; none of it is game code.

`data/plants.json` holds the plant registry as the picker sees it, for game version 4.2.4, the one version the commands support. `game` gives the version and the platform of the package the data was read from; a version's declared data is assumed to be the same on every platform. `plants` lists every declared plant type in declaration order with its alias, class, declared cost, the flags the filters read (`enabled`, `hero_properties`, `is_consumable`, `valid_stages`, `black_list_stages`), and `can_live_on_waves`, the declared `CanLiveOnWaves` flag that the flooded cell kind reads. `registry_order.configured_types` is the game's `PlantTypeOrder`, which the registry puts first. `artifact.plant_black_list` is the artifact's own black list. `sources` records the three game files the projection came from, with their SHA-256.

To move to a newer version, decode `PLANTTYPES`, `PROPERTYSHEETS` and `ARTIFACT` from its configuration package to JSON, outside this repository, and run `build-plants` with `--game-version` and `--platform`; the result replaces `data/plants.json`. If a fixture or a test still names the version being replaced, first move that version's file to `tests/fixtures/plants/VERSION.json`, where the tests find it.

`data/level-modules.json` holds, for game version 4.2.4, the objects that level definitions share: the stage and module objects of `LEVELMODULES`, keeping the data of the classes a description reads; the mutator tables of `LEVELMUTATORTABLES`; the classes of `LEVELMUTATORMODULES`; the cells of the `BOARDGRIDMAPS` grid maps those tables name; and the class of each grid-item type in `GRIDITEMTYPES`. An alias declared twice keeps both declarations. `sources` records the five files with their SHA-256. `build-level-modules` rebuilds it from a decoded package directory.

`data/tile-rules.json`, `data/previews.json` and the level descriptions are not tied to a version and are assumed to carry over; each measured record in the two rule files names the game version it was taken on in `game_version`.

`data/tile-rules.json` holds the named cell kinds. Each kind lists the plants its planting check rejects beyond the stage rule and the level's bans (`rejects`), or, for a flooded cell, the plant flag that admits a plant (`admits_flag`, the `can_live_on_waves` field of the plant data); a kind may also list the only plants it admits (`admits_only`). The kind `none` is built in. `measured` names the captures behind a kind and the game version each was taken on. To add a kind, read a source's candidate list on such a cell from the game, diff it against the model's list for that level and cost, and record the difference here.

`data/previews.json` describes the artifact screen's previews, by artifact. `evolution` describes the display board as the activation it runs: the board's stage and cell kind, the activation cell, the source plant the previews evolve, `spawn_max_cost` (the rank-4 spawn cost cut, on this board and in a level), and for each rank the source cells in planting order. The source's effective cost is an input of every prediction; its declared cost is the default. `devolution` gives for each rank the sizes of the shuffles its preview draws, in order. `measured` names the captures behind each rank and the game version each was taken on.

## Level descriptions

`data/levels/*.json` holds one description per level. It is the model's input contract: the declared facts the model reads, and where they came from.

- `id`, `name`, `stage`, `bans` (the seed bank's black list), `default_kind`, and `cells`, a map of COLUMN-ROW to kind for the cells whose kind differs from the default. Optional `width` and `height` default to 9 and 5.
- `entry_shuffles`, the sizes of the gravestone bags the level shuffles with the shared engine as it loads, in wave order; absent or empty for a level that shuffles nothing at entry. A decoded level definition gives them as the sum of `Count` over the `GravestonePool` of each `SpawnGravestonesWaveActionProps` that the wave manager's `Waves` list references, in wave order; an alias declared twice resolves to its first declaration, and an action no wave references builds nothing.
- `provenance` says where the facts came from. A description exported from a decoded level definition has `kind` `declared`, `resources` with the package path and SHA-256 of each file read, `observed` for the inputs the definition does not declare (the Pirate deck edge as `deck_columns`, the first Beach column that floods as `shore_from`), `stage_override` when the stage was supplied by hand, and `tier` when the description is of one difficulty tier. A description written from a capture or by hand has `kind` `capture` or `hand` and a `note`.
- `notes` are for the reader.

Declared initial gravestones are `none` cells, which cannot hold a plant; give `ground` for an activation once one has been destroyed. The plants a level protects are `none` cells as well: the artifact skips a protected plant as a source and its cell holds no other plant while it stands. A trap is ground, since a plant can stand on one. Plank rows are declared; the deck edge and the shore column are observed on the board, which is why they are recorded as observed inputs. Penny's Pursuit levels choose their protected plants and grid items by difficulty tier, through the level's mutator tables, so they are described per tier.

`convert-level` generates the descriptions with declared provenance from decoded level definitions, which are not redistributed, and they regenerate identically from their recorded inputs. It follows the definition's active references; an alias declared twice resolves to its first declaration. What it does not describe, the description's notes name: grid items of other kinds, plants placed at level start, a Beach tide without its observed shore column, references nothing declares, later declarations that differ from the first, and modules of classes that no matched activation has had, which may change the board or draw from the shared engine before the activation. A level whose file is not at hand can be described by hand from the seed-selection screen, which shows the bans, and from the board.

`pennys-pursuit-dark` was read from a capture in one Penny's Pursuit level whose definition was not identified; it describes that level only. `rift-1565-tier2` is the Penny's Pursuit level `RIFT_1565` at tier 2, whose protected Red Stingers stand on 6-1, 6-3 and 6-5 between its traps.

The Endless examples are `arthurs-challenge` (Dark Ages) and `tiki-torch-er` (Big Wave Beach). Arthur's Challenge uses a ground baseline; supply standing gravestones as `none`. Tiki Torch-er defaults to ground in columns 1–4 and water in columns 5–9; supply `beach_pad` for Lily Pads and `beach_shore` for exposed sand at activation.

## Capture fixtures

Each fixture file names the game version it was read from in `game_version`, and the expectations written into the test files name theirs in `CAPTURED_ON`. The tests replay each with that version's plant data: the bundled data for 4.2.4, and for 4.2.2 the plant data kept as `tests/fixtures/plants/4.2.2.json`. `tests/test_search.py` names 4.2.2 for all of its cases: some expectations are offsets captured on it, and its route cases show the properties their comments name with that data, not all of them with 4.2.4's. The other tests use the bundled data. A test requires each plant that the cell kinds, the previews and the levels name to be declared in the bundled data and in every kept projection, so a renamed plant cannot silently drop a rule.

`tests/fixtures/pools.json` holds ordered candidate lists read from the running game, keyed by level, cell kind and source cost, plus the two preview pools; the tests require the model to reproduce each of them in order.

`tests/fixtures/rank4-captures.json` retains ten rank-4 activations in normal levels: inputs, selections, ordered-pool hashes, draw intervals and trace hashes, with no process or account data. Some planting orders were reconstructed by reversing the recorded processing order; those cases are marked. The starting offsets were identified from recorded draws, so these are replay cases rather than forecasts, run at those positions inside their levels, after any entry shuffles. Captures 1 to 3 belong to one process and 4 to 10 to a later one whose capture 4 begins at offset 2,874, with unrecorded gaps of 10 and 78 outputs before captures 7 and 9. The 10 before capture 7 match the Dark Ages 4 entry from where capture 6 ended; what consumed the 78 was not recorded. The model regenerates every draw from the default seed; the fixture supplies none.

`tests/fixtures/preview-captures.json` retains two display-board captures: a fresh-launch route of seven rank-1 and six rank-4 previews, and previews 10 and 11 of a rank-1 route, both with Sunflowers at effective cost 47. Each preview lists its selections with cell, candidates, draw interval and placement, the recorded plant-add order, and the positions of the outputs recorded inside a Draftodil's add call; the tests replay every row, effect and offset. The second capture starts where the model put the nine reported previews before it.

`tests/fixtures/preview-captures-4.2.4.json` retains five fresh-launch captures taken on 4.2.4 with Sunflowers at effective cost 37: a rank-3 preview between two rank-1 previews; one and two Devolution previews before a rank-1 preview; a route of thirteen previews that runs rank-3 previews next to rank-4 ones and Devolution previews after Evolution previews of each rank; and a rank-1, a rank-3, a Devolution and a rank-1 preview. The Evolution previews are recorded as in the 4.2.2 file; a Devolution preview lists the draw interval of each of its shuffles, since the captures record its draws but not its lists. The tests replay every row, interval and offset.

`tests/test_level_entry.py` holds, written inline, three fresh-launch activations in Dark Ages 19 and 21 with the plant data of the version they were read on: the outputs each level's entry consumed, the selections after them, and the row shuffle of an evolved Draftodil whose row held plants outside the area; the outputs the Dark Ages 4 entry consumed in an earlier recording; the Dark Ages 4 entry that fills the gap before capture 7; and a recipe `plan` produced for Arthur's Challenge, a level with no gravestone action, played as written after three previews: no output at its entry, its seven selections, and the row shuffles of its two Draftodils, counting the sources still standing in their rows.

`tests/fixtures/rank4-followups.json` retains three Beach activations that test the placement rules: B, a Sea-shroom over water whose replacement and extra support both selected Lily Pad; A, a Puff-shroom on dry shore receiving a Lily Pad beneath it; and Cactus, a dry-shore replacement rejected after the pad appeared. B and Cactus were forecast before play from declared preview sequences; A's offset was identified afterwards. Each case records the plant-add call order, and `placed` expectations are asserted only where the terrain stayed unchanged, so the Cactus case excludes its flooded column 6. `captured_stream_end` counts the outputs recorded after the last selection, which `stream_end` does not.

`tests/fixtures/search-equality.json` is computed, not captured. For each of its requests it lists level entries drawn at random and the recipe that `tests/reference_search.py`, the recipe search as it stood before its states were merged, returns at each of them; the tests require `plan`'s search to return the same recipe at every entry. Its note says how the entries were drawn, and `python3 tests/reference_search.py check` recomputes them. Its `game_version` names the plant data the recipes were computed with, which the tests select as they do for a capture.
